# Django Blog System with Traffic Control

PythonAnywhereの無料枠（Beginner Plan）という、非常に制限されたインフラリソース下でシステムの可用性を最大化することを目的とした、Djangoブログアプリケーションのプロトタイプです。

## 1. 開発背景と技術的制約

本プロジェクトは、以下の制約を持つ環境へのデプロイを前提に設計されています。

- シングル・Webワーカー: 並列リクエスト処理が不可。1つの重い処理や連続アクセスが、全ユーザーのサービス停止に直結します。
- CPU時間制限: 1日2,000秒を超えるとスロットリングが発生し、レスポンス速度が極端に低下します。
- 外部通信制限: プロキシ経由の許可リストのみ通信可能。外部Redis等の独自プロトコルを利用したミドルウェアの導入が困難です。

## 2. トラフィック制御とアクセス管理

インフラの脆弱性をアプリケーション層のロジックで補完するため、以下の機能を実装しました。

### トークンバケットによる変動コスト制流量制限

- 独自のアルゴリズムにて、バーストアクセスを許容しつつ定常レートを絞る機能を実装しています。
- 処理の負荷に応じた「変動コスト制」を導入しました。
  - 閲覧等の軽い処理: 1.0コスト
  - ログイン処理: 2.0コスト
  - 記事投稿や編集等の重い処理: 3.0コスト
- 負荷の高い連続アクセスからサーバーリソースをより効果的に守ります。

- 更新ロジック: `新たなトークン数 = min(最大容量, 現在のトークン数 + 経過時間 × 補充レート)`
- 設定: `0.5 token/sec`（補充）、`5.0 tokens`（最大貯蔵）

本プロジェクトでは、アルゴリズムの挙動が視覚的・体感的に分かりやすいよう、トークン補充レートおよび最大容量は意図的にやや厳しめの値に設定しています。

### Middlewareによる階層防御とセッション管理

- Viewが実行される前の段階でリクエストを評価し、制限超過時はDjango本体の処理を走らせず即座にレスポンス（`429 Too Many Requests`）を返すことでサーバー負荷を最小化します。
- 未認証ユーザーを案内ページへ誘導し、ログインまたはゲストとしての閲覧を選択させる多層的なアクセス制御を実装しています。
- 静的ファイル（CSS等）へのアクセスは制限から除外しています。

### Cache抽象化による状態管理

- Redisが使えない制約下で、Djangoのローカルメモリキャッシュを活用しつつ、将来的なインフラ移行を見据えた疎結合設計としています。

## 3. 技術スタック

- Backend: Django 6.0 (Python 3)
- Database: SQLite3
- Storage/Cache: LocMemCache (Django Local-memory)
- Infrastructure: PythonAnywhere
- Configuration: python-dotenv (環境変数管理)

## 4. セットアップと環境変数の設定

本プロジェクトではセキュリティ向上のため、シークレットキーなどを環境変数として管理しています。ローカル環境での実行手順は以下の通りです。

1. プロジェクトルートまたは `blog` ディレクトリ内に `.env` ファイルを作成し、以下の内容を設定してください。

```text
DJANGO_SECRET_KEY=あなたのシークレットキーをここに記述
```

2. コマンドを実行して環境を構築します。

```bash
pip install -r requirements.txt
python manage.py migrate
python manage.py test
python manage.py runserver
```

## 5. 自動テスト

システムの信頼性を担保するため、自動テストを実装しています。
- データベースへの正常な保存
- 未ログイン時の適切なリダイレクト制御
- 変動コスト制によるトラフィック制限の正確な動作

これらをコマンド一つで検証できます。
